# OntoFlow 개괄 설계

> 제품 방향과 컴포넌트 경계를 정의한다.
> 데이터 모델·테이블·검증 규칙은 상세 설계 문서에서 다룬다.

---

## 1. 제품 목표

### 1.1 올해의 범위

**실무 적용 수준의 워크플로우 매니저와 온톨로지 매니저를 완성한다.** 그 위에 붙는 것들은 조립형 컴포넌트로 두고, 계약만 미리 고정한다.

```text
코어 (실무 적용)
  Ontology Manager     업무 의미, 검증 기준, 영속 지식을 소유한다
  Workflow Manager     업무 절차와 실행을 소유한다
  Button/Form UI       명시적 실행 인터페이스

앞단 조립 (모듈)
  Conversational Input     자연어 → 슬롯
  Document / API Input     문서·외부 시스템 → 슬롯

뒷단 조립 (초기 검증 범위)
  Gate / WriteBack         변경 후보 승인과 영속 반영

측면 조립 (후속 범위)
  Automate                 이벤트 트리거 → 실행
```

### 1.2 소유권 원칙

```text
업무 의미와 타입, 영속 지식은 Ontology Manager 가 소유한다.
업무 로직과 실행은 Workflow Manager 가 소유한다.
대화는 슬롯을 채우고 실행을 제안할 뿐 소유하지 않는다.
Gate 는 승인 경계를 더할 뿐 실행을 대신하지 않는다.
자동화는 사람의 클릭을 대신할 뿐 우회하지 않는다.
```

## 2. 왜 버튼식이 먼저인가

대화형 업무 자동화를 먼저 만들면 슬롯 채우기, 되묻기, 예외 처리 로직이 **대화 엔진에 종속된다.** 그 뒤에는 이를 독립적인 워크플로우 코어로 분리하기 어렵다.

| 항목 | 버튼식 코어 | 대화식 단독 |
|---|---|---|
| 파라미터 확인 | 명시적 | 해석이 필요하다 |
| 테스트 | 결정론적 | 확률적 평가가 필요하다 |
| 장애 대응 | 수동 입력으로 우회 | 인식 실패 시 대안이 없다 |
| 권한 관리 | 버튼·액션 단위 | 발화 의도 해석에 의존 |
| 실무 도입 | 빠르다 | 고객별 튜닝 부담이 크다 |

버튼식 코어가 먼저 있으면 **대화는 같은 슬롯을 채우는 어댑터가 된다.**

```text
입력 경로가 다르다        버튼 · 폼 · 대화 · 문서 · 외부 API
채우는 대상은 같다        상태 슬롯

→ 입력 경로가 늘어도 코어는 늘지 않는다
```

## 3. 컴포넌트 구조

```text
      ┌──────────── 입력 컴포넌트 ────────────┐
      │  Button/Form   Conversational        │
      │  Document      External API          │
      └───────────────────┬──────────────────┘
                          │  슬롯을 채운다
                          ▼
      ┌─────────── Workflow Manager ─────────┐   ◆ 실무 적용
      │  정의 · 제어 선 · 바인딩 · 실행 상태    │
      │  정적 검사 · dry-run                  │
      └───────────────────┬──────────────────┘
                          │  기준 참조 / 승격 판정
                          ▼
      ┌─────────── Ontology Manager ─────────┐   ◆ 실무 적용
      │  타입 기준 · 영속 지식 · 변경 이력      │
      │  일괄 등록 · Unified Validator        │
      └───────────────────┬──────────────────┘
                          │
                          ▼
      ┌──────────── 확장 컴포넌트 ────────────┐   ○ 초기 검증 범위
      │  Gate → WriteBack                    │
      │  Automate (후속 범위)                  │
      └──────────────────────────────────────┘
```

| 컴포넌트 | 올해 수준 | 역할 |
|---|:---:|---|
| Ontology Manager | **실무 적용** | 타입 기준, 영속 지식, 일괄 등록, 변경 절차, 변경 이력, 검증 |
| Workflow Manager | **실무 적용** | 정의, 제어 선, 바인딩, 실행 상태, dry-run |
| Button/Form UI | **실무 적용** | 명시적 업무 실행 |
| Conversational Input | 모듈 연동 | 자연어를 슬롯 채움과 실행 제안으로 변환 |
| Gate / WriteBack | 초기 검증 범위 | 변경 후보 승인과 반영 계약 검증 |
| Automate | 후속 범위 | 이벤트 조건 기반 자동 실행 |

## 4. 조립 계약의 원칙

컴포넌트를 "조립형"이라 부르려면 조건이 있다. **셋 중 하나라도 어긋나면 그것은 조립 부품이 아니라 코어의 일부다.**

```text
① 코어가 그 컴포넌트 없이 완결된다
② 계약면이 한 곳으로 수렴한다
③ 실패해도 코어 경로로 돌아갈 수 있다
```

| 컴포넌트 | ① 코어 완결 | ② 계약면 | ③ 폴백 |
|---|---|---|---|
| Conversational Input | 버튼으로 같은 일을 한다 | **상태 슬롯 하나** | 수동 입력·버튼 실행 |
| Gate / WriteBack | 일괄 등록과 직접 편집이 있다 | **변경 후보 하나** | 직접 편집 경로 |
| Automate | 사람이 실행한다 | **실행 시작 하나** | 수동 실행 |

**계약 설계에도 비용이 들므로, 지금 계약을 고정할 것과 후속 범위로 둘 것을 구분한다.**

| 컴포넌트 | 지금 계약을 만드는가 | 이유 |
|---|:---:|---|
| Conversational Input | **만든다** | 슬롯 구조에 직접 얹힌다 |
| Gate / WriteBack | **만든다** | 실행 상태와 영속 지식 사이에 끼어든다 |
| Automate | **한 줄만** | 접점이 "실행을 시작한다" 하나뿐이다 |

```text
자동화의 계약
  트리거는 실행을 시작한다. 그 뒤는 버튼식 실행과 동일하다.
```

## 5. Ontology Manager

### 5.1 소유하는 것

| 대상 | 내용 |
|---|---|
| 타입 기준 | 객체·속성·공유속성·관계·액션·워크플로우 유형 |
| 영속 지식 | 객체 인스턴스, 속성값, 관계 인스턴스 |
| 변경 절차 | 제안 → 영향 분석 → 승인 → 적용 |
| 변경 이력 | 기준과 영속 지식이 실제로 바뀐 기록 |
| 일괄 등록 | 파일·API로 들어오는 대량 정의·데이터 |
| 검증 | 타입·범위·열거·패턴·필수·참조 무결성·카디널리티 |

**공유 속성은 최소형으로라도 올해 넣는다.** 여러 객체 유형에 같은 속성이 흩어진 뒤 합치려면 참조를 전부 옮겨야 한다.

### 5.2 기준이 검증에 실제로 개입한다

스키마 테이블이 존재하는 것만으로는 온톨로지가 작동한다고 할 수 없다. **기준이 다음 지점에서 실제로 조회된다.**

```text
슬롯 이름을 고를 때        기준 조회 드롭다운
노드 선언을 저장할 때      정적 검사
슬롯에 값을 쓸 때          타입·범위·열거 검증
일괄 등록을 받을 때        항목별 검증
직접 편집을 저장할 때      동일 검증
승격 판정을 할 때          기준값과 필수 여부
```

### 5.3 개념 범위

| 개념 | 판단 |
|---|:---:|
| 객체·속성·관계·액션 타입 | **핵심 구현** |
| 공유 속성 정의 | **최소 구현** |
| 영속 인스턴스와 값 이력 | **핵심 구현** |
| 일괄 등록 | **핵심 구현** |
| 인터페이스 타입 (다형 계약) | 후순위 |
| 객체 집합 정의 (질의 저장) | 후순위 |
| 데이터소스 매핑 | 제한 구현 |
| 고급 권한·보안 모델 | 후순위 |

### 5.4 정의 변경과 데이터 변경은 다른 절차다

| 절차 | 대상 | 소유 | 올해 |
|---|---|---|---|
| 타입 변경 승인 | 정의 자체 (스키마) | **온톨로지 매니저** | **실무 적용** |
| Gate 승인 | 인스턴스 값 (데이터) | Gate 확장 | 초기 검증 범위 |

Gate가 초기 검증 범위라고 해서 타입 변경도 승인 없이 되는 것은 아니다.

## 6. 영속 지식의 네 진입 경로

### 6.1 경로

```text
① ABox 일괄 등록      파일·API·UI  →  검증  →  적용
② ABox 직접 편집      관리자 화면  →  권한 확인  →  검증  →  적용
③ TBox 변경          제안  →  영향 분석  →  승인  →  적용
④ 워크플로우 승격      슬롯  →  승격 판정  →  Gate 후보  →  승인  →  적용
```

### 6.2 결론 셋

**모든 경로가 같은 검증기와 같은 적용 경계를 지난다.** 검증 기준이 경로마다 달라지면 같은 값이 한쪽에서는 통과하고 다른 쪽에서는 실패한다.

**정의를 바꾸는 요청은 예외 없이 ③을 탄다.** 일괄 등록이든 관리자 화면의 단건 수정이든, 승인된 변경 제안 없이는 정의가 바뀌지 않는다. 이것은 선언이 아니라 적용 경계가 강제한다.

**Gate는 ④에만 개입한다.** ①②③이 있으므로 Gate 없이도 영속 지식이 관리된다.

| Gate 정식 운영 전 | Gate 정식 운영 후 |
|---|---|
| ①②③ 정상 동작 | ①②③ 그대로 |
| ④는 승격 **판정**까지만 | ④에 승인 단계가 붙는다 |
| 워크플로우 결과는 슬롯과 dry-run 리포트로 확인 | 후보 → 승인 → 반영 |

**승격 조건을 판정하는 것은 코어이고, 그 결과로 후보를 만들어 승인받는 것이 Gate다.**

### 6.3 권한도 갈라진다

| 권한 | 대상 |
|---|---|
| `ontology_edit_allowed` | ABox 직접 편집 |
| `type_change_propose_allowed` | TBox 변경 제안 |
| `type_change_approve_allowed` | TBox 변경 승인 |
| `writeback_allowed` | Gate WriteBack |

**ABox 편집 권한으로는 정의를 바꿀 수 없다.**

## 7. Unified Validator

**검증기는 하나다.**

타입·범위·열거값·패턴·필수값·참조 무결성·카디널리티 검증을 한 컴포넌트가 담당한다. 슬롯 쓰기, dry-run, 승격 판정, 일괄 등록, 직접 편집, 영향 분석이 모두 같은 검증기를 호출한다.

**호출자마다 다른 것은 실패 처리 정책뿐이다.** 어떤 호출자는 거부하고, 어떤 호출자는 항목을 건너뛰고, 어떤 호출자는 리포트에 기록만 한다.

**검증 결과 형식도 하나다.** dry-run 리포트·일괄 등록 리포트·영향 분석 리포트가 같은 형식을 쓰므로 표시 컴포넌트를 공유한다. 형식이 갈리면 화면이 두 벌이 되고, 두 벌은 반드시 어긋난다.

## 8. Workflow Manager

### 8.1 제공 기능

| 기능 | 설명 |
|---|---|
| 워크플로우 정의 | 노드와 제어 선을 저장한다 |
| 역할 선언 | 이 절차가 다루는 대상과 그 타입을 선언한다 |
| 슬롯·액션 바인딩 | 노드가 읽고 쓰는 슬롯과 실행할 액션을 연결한다 |
| 정적 검사 | 저장·실행 전에 선언과 매핑의 어긋남을 잡는다 |
| 실행 상태 | 실행 중 값을 격리된 슬롯으로 관리한다 |
| 이력 | 슬롯 변경, 노드 진입, 외부 호출을 각각 남긴다 |
| **dry-run** | **반영 없이 파라미터·매핑·검증 결과를 확인한다** |

### 8.2 값은 선이 아니라 이름으로 흐른다

캔버스의 선은 **실행 순서만** 뜻한다. 값은 이름 붙은 슬롯에 쓰고 이름으로 읽는다.

```text
데이터 선 없음   값이 3개 노드에서 쓰여도 선이 늘지 않는다
제어 선만 있음   순서 · 분기 · 반복 · 병렬
```

**단 이름은 자유 문자열이 아니다.** 기준에 등록된 속성에서 파생되고, 대상 역할까지 함께 지목한다.

```text
subject.장력      단일 대상일 때는 역할을 생략하고 "장력" 으로 쓴다
source.장력       두 대상을 비교할 때만 역할을 드러낸다
```

### 8.3 액션은 객체를 소비하고 생성한다

```text
createAppointment
  required_object_roles   patient, doctor
  produced_object_roles   appointment
```

생성 대상 역할은 **액션이 성공한 뒤 바인딩된다.** 아직 대상이 없는 워크플로우가 특수 케이스가 아니라 정규 모델이 된다.

### 8.4 dry-run이 반영 없이 품질을 확인한다

```text
dry-run 은 끝까지 실행하되
  슬롯을 정상적으로 채우고
  검증기를 호출하고
  승격 조건을 평가하고
  변경 후보는 만들지 않으며
  적용 경계를 호출하지 않는다
```

산출은 검증 리포트다. 실행된 경로, 미충족 필수 슬롯, 슬롯별 검증 결과, 근거 유무, 액션 호출 요약, **승격 가능 여부와 미충족 항목 목록**, 반영되었다면 바뀌었을 값의 미리보기.

**액션이 dry-run에서 실제로 호출되는지는 액션 정의가 정한다.** 부작용 수준을 액션마다 선언하며, 기준을 바꾸는 액션은 dry-run에서 실행되지 않는다.

## 9. 일괄 등록

**대량 적재는 고객 온보딩의 본체다.** 파일·API로 들어온 원본을 항목으로 쪼개고, 검증한 뒤, 리포트를 보고 적용한다.

**ABox와 TBox는 통제 강도가 다르다.**

| | ABox 일괄 적재 | TBox 일괄 변경 |
|---|---|---|
| 대상 | 인스턴스·속성값·관계 | 정의 전체 |
| 적용 모드 | 전체 적용 / 부분 적용 선택 | **전체 적용 고정** |
| 승인 | **불필요** | **필수** |
| 경유 | 바로 적용 | **변경 제안 → 영향 분석 → 승인** |

**속성 하나를 바꾸는 데도 승인이 필요한데, 500개를 한 번에 바꾸는 것이 검증만으로 통과하면 통제 강도가 거꾸로 된다.** TBox는 검증 기준 자체를 바꾸므로 기준이 바뀌면 기존 데이터 전체의 유효성이 흔들린다. 규모가 클수록 영향 분석이 더 중요해진다.

정의 일부만 적용되면 기준이 불완전한 상태로 남으므로 **TBox는 부분 적용을 선택할 수 없다.**

---

## 10. 변경 이력

### 10.1 두 이력을 구분한다

| 이력 | 의미 | 소유 |
|---|---|---|
| 슬롯 변경 이력 | 워크플로우 실행 중 슬롯값이 어떻게 바뀌었는가 | Workflow Manager |
| 온톨로지 변경 이력 | 기준 또는 영속 인스턴스가 **실제로** 바뀌었는가 | Ontology Manager |

워크플로우가 값을 계산했다고 해서 곧바로 영속 인스턴스가 바뀌지 않는다.

### 10.2 후보와 이력은 다르다

| 대상 | 성격 | 생성 시점 |
|---|---|---|
| 변경 후보 | **제안** — 승인 대기 | 워크플로우 승격 시 |
| 변경 이력 | **사실** — 실제 일어난 변경 | **적용될 때마다 항상** |

**후보는 반려될 수 있으므로 이력이 아니다.** 이력은 승인 여부와 무관하게 남는다. 일괄 등록과 직접 편집은 후보를 거치지 않고 이력을 남기고, 워크플로우 경로는 후보가 반영될 때 이력을 남긴다.

## 11. 대화식 입력 컴포넌트

### 11.1 흐름

```text
사용자 발화
  → 의도 인식        어느 워크플로우인가
  → 실행 시작        실행 단위 발급
  → 대상 바인딩      역할에 인스턴스 연결
  → 슬롯 채움        추출값 기록
  → 되묻기           미충족 필수 슬롯 질문
  → 실행 제안        버튼식과 같은 엔진으로 실행
```

**의도 인식이 실행 시작보다 앞선다.** 어느 워크플로우인지 정해져야 실행 단위가 생기고, 그래야 슬롯을 담을 곳이 생긴다. 그전에 뽑힌 값은 세션 버퍼에 담고, 실행이 시작될 때 슬롯으로 옮기며 그 시점에 검증한다.

### 11.2 하지 않는 것

```text
워크플로우 정의를 바꾸지 않는다
타입 기준을 바꾸지 않는다
액션을 우회 실행하지 않는다
영속 지식에 직접 반영하지 않는다
되묻기 순서를 스스로 정하지 않는다
```

**마지막 항목은 경계가 흐려지기 쉽다.** 세 슬롯이 비었을 때 무엇부터 물을지를 대화 모듈이 정하면 그것은 이미 업무 지식이다.

```text
무엇을 언제 물을지  →  노드 슬롯 선언이 정한다 (코어)
어떻게 말할지       →  대화 모듈이 정한다 (부품)
```

이 분리가 있으면 **대화 모듈은 렌더러가 된다.** dry-run이 만드는 미충족 항목 목록이 그대로 되묻기 큐가 된다.

### 11.3 버튼 입력과 대화 입력은 근거 수준이 다르다

| 구분 | 버튼·폼 | 대화 |
|---|---|---|
| 값의 성격 | 확정값 | 확률값 |
| 신뢰도 | 해당 없음 | 함께 기록해야 한다 |
| 확인 필요 | 대개 불필요 | 낮은 신뢰도는 확인 질문 |
| 원문 보존 | 선택 | **필수** |

---

## 12. Gate 컴포넌트

| 항목 | 올해 |
|---|---|
| 변경 후보 저장 | 최소 구현 |
| 승인 화면 | 최소 구현 |
| WriteBack | 모의 흐름 |
| 충돌·실패 상태 | **계약만 고정** |
| 다단계 승인 · 권한 세분화 | 후순위 |
| 운영 대시보드 · 감사 리포트 | 후순위 |

Gate는 §6.1의 ④번 경로에만 개입한다.

```text
슬롯 → 승격 판정 → [ Gate 후보 → 승인 ] → WriteBack → 적용 → 이력
                     └── 확장 컴포넌트 ──┘
```

**WriteBack도 저장소를 직접 건드리지 않는다.** 다른 세 경로와 같은 적용 경계를 호출하므로 검증과 이력이 동일하게 이루어진다.

---

## 13. 자동화 컴포넌트

```text
트리거          효과
  일정 도래       워크플로우 실행
  객체 상태 변경   액션 실행
  외부 이벤트     알림 발송
  임계값 초과     변경 후보 생성
```

**자동화는 워크플로우 엔진을 우회하지 않는다.** 사람이 누를 버튼을 시스템이 대신 누르는 것에 가깝다. 올해는 계약 한 줄만 고정한다.

## 14. 예시 — 병원 예약

### 14.1 정의

```text
ObjectType     Patient · Doctor · Department · Appointment
RelationType   Patient HAS_APPOINTMENT Appointment
               Doctor  HAS_SLOT        Appointment
ActionType     verifyPatient · findAvailableSlots
               createAppointment · sendNotification
```

### 14.2 버튼식 흐름

```text
1. 환자 선택   2. 진료과 선택   3. 의사 선택
4. 예약 가능 시간 조회   5. 예약 생성   6. 알림 발송
```

```text
역할   patient · department · doctor · appointment
       appointment 는 createAppointment 가 생성한다

슬롯   patient.name · patient.phone · department.code
       doctor.id · doctor.available_slots
       appointment.requested_time · appointment.status
```

### 14.3 같은 흐름에 대화를 얹는다

```text
"김민수 환자 내일 오전 정형외과 예약해줘"

의도 인식   → 병원예약 워크플로우
슬롯 채움   → patient.name = 김민수
            → department.name = 정형외과
            → appointment.requested_time  원문 "내일 오전" → 정규화
되묻기      → doctor 미지정. 선언 순서에 따라 질문
실행        → 버튼식과 같은 엔진
```

**채워지는 슬롯이 버튼식과 동일하다.** 대화가 실패하면 사용자는 버튼 화면으로 돌아가 같은 슬롯을 직접 채운다.

### 14.4 영속 반영

```text
Gate 없을 때   예약 결과를 직접 편집 경로로 적용 → 이력 기록
Gate 있을 때   승격 판정 → 후보 → 승인 → 반영 → 이력 기록
```

어느 경로든 최종 영속 상태와 이력은 같은 방식으로 남는다.

### 14.5 시작 방식이 다른 두 예시

| 예시 | 실행을 시작하는 것 | 문서 |
|---|---|---|
| 병원 예약 | 사람이 버튼·폼으로 시작한다 | [병원 예약 예시](../../examples/ko/hospital-reservation.md) |
| 공장 자동 정비 지시 | 설비 이벤트가 조건을 충족하면 시작한다 | [공장 자동 정비 지시 예시](../../examples/ko/factory-maintenance-auto.md) |

두 예시는 시작 방식만 다르다. 슬롯을 채우고, 기준으로 검증하고, 액션을 실행하고, 적용 경계를 지나 이력을 남기는 구조는 같다.

## 15. 도입 로드맵

### 15.1 실무 적용 코어

| 단계 | 내용 |
|:---:|---|
| **Core-1** | 타입 기준 기본 구조 |
| **Core-2** | 영속 지식 저장소 · 적용 경계 · 변경 이력 |
| **Core-3** | **Unified Validator 최소 규칙셋** |
| **Core-4** | 일괄 등록 — Job·Item, ABox 적재, dry-run |
| **Core-5** | TBox 변경 제안 · 영향 분석 · 승인 |
| **Core-6** | 워크플로우 정의 · 역할 · 노드 · 제어 선 |
| **Core-7** | 슬롯 선언 · 액션 바인딩 · 정적 검사 |
| **Core-8** | 실행 · 역할 바인딩 · 상태 슬롯 |
| **Core-9** | 슬롯 변경 이력 · 액션 실행 로그 · 근거 |
| **Core-10** | 버튼식 실행 · dry-run 리포트 |

**Validator가 일괄 등록보다 앞선다.** 일괄 등록이 첫 대량 검증 호출자이므로, 검증기 없이 대량 데이터를 받으면 이후 판정 결과가 달라진다.

### 15.2 조립형 컴포넌트

| 단계 | 내용 |
|:---:|---|
| Conv-P1 ~ P3 | 의도 인식 · 되묻기 · 발화 근거 |
| Gate-P1 ~ P3 | 변경 후보 · 승인 화면 · WriteBack 모의 흐름 |
| Auto-1 ~ 2 | 이벤트 트리거 · 자동 실행 (후속) |

### 15.3 네 질문은 Core-10에서 닫힌다

| 단계 | 답하는 것 |
|:---:|---|
| Core-1 ~ 2 | 스키마가 어디에 쓰이는가 — 정의와 그 정의를 따르는 데이터 |
| Core-3 ~ 5 | 스키마를 어떻게 동적으로 바꾸는가 · 데이터 품질에 어떻게 기여하는가 |
| Core-6 ~ 10 | 결정론적 판단에 어떻게 기여하는가 |
| 확장 단계 | 답을 조직 데이터에 반영하는 경로를 늘린다 |

**확장은 답을 완성하는 단계가 아니다.**

## 16. 확정 대기 항목

상세 설계의 미결 항목(`D-N`)과 매핑한다.

| # | 판단 | 선택지 | 상세 | 시점 |
|---|---|---|:---:|---|
| **O-1** | 공유 속성의 스코프 | 전역만 / 프로젝트 확장 허용 | D-2 | Core-1 |
| **O-2** | 일괄 등록 원본 보존 | 참조만 / 사본 보관 | D-5 | Core-4 |
| **O-3** | TBox 일괄 변경의 승인 단위 | Job 전체 / 항목별 | D-7 | Core-5 |
| **O-4** | **영향 분석의 인스턴스 검사 범위** | 전량 / 표본 / 비동기 전량 | **D-8** | **Core-5** |
| **O-5** | dry-run 리포트 보존 | 휘발 / 실행 단위 보존 / 추세 비교 | D-14 | Core-10 |
| **O-6** | 대화 모듈의 조달 | 자체 개발 / 외부 모델 연동 / 혼합 | — | Conv-P1 |
| **O-7** | 되묻기 정책의 소유 | 선언에 고정 / 도메인별 오버라이드 허용 | D-12 | Conv-P2 |
| **O-8** | 데이터소스 매핑 범위 | 수동 등록만 / 적재 파이프라인 연동 | — | Core-4 이후 |

**O-4의 영향 범위가 가장 크다.** 전량 검사는 정확하지만 대량 데이터에서 승인이 오래 걸리고, 표본 검사는 빠르지만 적용 시점에 실패가 드러난다. 선택에 따라 변경 제안의 상태 집합과 화면 흐름이 달라지므로 **Core-5 설계 착수 전에 확정한다.**

나머지 미결은 상세 설계 §19를 참조한다.

## 17. 최종 판단

목표는 대형 데이터 운영 플랫폼 전체를 복제하는 것이 아니다. 더 좁고 선명하다.

```text
실무 적용 수준의 온톨로지 매니저
  타입 기준 · 영속 지식 · 일괄 등록 · 변경 절차 · 단일 검증기

실무 적용 수준의 워크플로우 매니저
  정의 · 바인딩 · 실행 상태 · 정적 검사 · dry-run

명시적 버튼식 업무 자동화

앞단 대화식 입력 모듈
뒷단 Gate / WriteBack 확장
후속 자동화 확장
```

이 구조의 이득은 세 문장으로 요약된다.

> **영속 지식에 이르는 모든 경로가 같은 검증과 같은 적용 경계를 지난다.**
> **정의를 바꾸는 모든 요청은 승인을 경유하며, 그것을 적용 경계가 강제한다.**
> **대화 모델, 승인 정책, 자동화 트리거가 바뀌어도 코어 엔진과 기준은 흔들리지 않는다.**
