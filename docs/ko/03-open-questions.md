# 공개 검토 주제

이 문서는 외부 리뷰가 필요한 설계 주제를 정리합니다.

각 항목은 OntoFlow가 이미 선택한 기본 방향을 먼저 설명하고, 그 방향을 더 낫게 만들기 위해 어떤 의견을 받고 싶은지 적습니다. 아래 질문은 결론이 없는 질문이 아니라 **토론을 시작하기 위한 예시 질문**입니다.

## 1. 워크플로우 상태 전달

### 배경

업무 절차를 실행하려면 한 단계에서 만들어진 값이 다음 단계로 전달되어야 합니다. 예를 들어 병원 예약에서는 선택된 환자, 진료과, 의사, 희망 일시, 예약 가능 시간이 단계마다 이어집니다.

### 현재 기준

OntoFlow는 노드 사이에 값을 직접 연결하는 데이터 선보다, 이름 있는 `State Slot`에 값을 저장하고 각 노드가 필요한 슬롯을 읽고 쓰는 방식을 우선합니다.

```text
제어 흐름   노드 A -> 노드 B -> 노드 C
값 전달     selected_patient, requested_date, available_slot 같은 상태 슬롯
```

이 방식은 전체 실행 중 어떤 값이 언제 바뀌었는지 추적하기 쉽고, 외부 API나 MCP 도구 호출 결과도 같은 상태 이력으로 남길 수 있습니다.

### 의견을 받고 싶은 지점

- 상태 슬롯 방식이 실제 업무 자동화에서 충분히 직관적인가
- 노드 간 데이터 선이 꼭 필요한 화면 또는 개발자 경험이 있는가
- 병렬 분기와 반복 실행에서 상태 슬롯 이름과 역할을 어떻게 보여주는 것이 좋은가

### 예시 질문

워크플로우 값은 노드 간 데이터 선으로 전달해야 할까요, 아니면 이름 있는 상태 슬롯으로 관리해야 할까요?

## 2. 온톨로지 기준의 개입 범위

### 배경

온톨로지는 업무 객체의 타입, 속성, 관계, 작업 정의를 관리합니다. 문제는 이 기준이 워크플로우 실행 중 어디까지 개입해야 하는가입니다.

### 현재 기준

OntoFlow는 온톨로지 기준이 다음 지점에 개입해야 한다고 봅니다.

- 객체 역할과 슬롯 타입을 정의한다.
- 슬롯에 들어오는 값을 검증한다.
- 실제 업무 데이터로 반영되는 쓰기를 제약한다.
- 값이 왜 바뀌었는지 설명할 수 있는 근거를 제공한다.

### 의견을 받고 싶은 지점

- 온톨로지 기준이 너무 강하게 개입해 업무 설계를 느리게 만들 가능성
- 실무자가 타입과 속성을 쉽게 고를 수 있는 UI 방식
- 아직 타입이 확정되지 않은 초기 설계 값을 어떻게 임시로 다룰지

### 예시 질문

온톨로지 기준은 워크플로우 실행 중 어디까지 개입해야 할까요?

## 3. 대화식 입력의 위치

### 배경

사용자는 버튼이나 폼 대신 자연어로 "김OO 환자 다음 주 오전 예약 잡아줘"처럼 요청할 수 있습니다. 이때 대화식 입력을 워크플로우 엔진 안에 넣을지, 별도 입력 컴포넌트로 둘지 결정해야 합니다.

### 현재 기준

OntoFlow는 대화식 입력을 앞단 컴포넌트로 봅니다. 대화는 워크플로우 실행 후보와 슬롯값 후보를 제안하지만, 실행의 주체는 `Workflow Manager`입니다.

```text
사용자 발화 -> Conversational Input -> 실행 후보 / 슬롯값 후보 -> Workflow Manager
```

### 의견을 받고 싶은 지점

- 대화식 입력이 만들어낸 값의 신뢰도와 근거를 어떻게 보여줄지
- 사용자가 대화 결과를 확인하고 버튼으로 실행하는 흐름이 충분한지
- 대화 실패 시 폼 입력으로 자연스럽게 돌아가는 UI 방식

### 예시 질문

자연어 입력은 워크플로우 엔진의 일부여야 할까요, 앞단 입력 컴포넌트여야 할까요?

## 4. Gate와 승인 경계

### 배경

업무 절차가 만든 결과가 실제 업무 데이터에 바로 반영되면 위험할 수 있습니다. 특히 외부 시스템 반영, 고객 데이터 수정, 기준 변경은 검토와 승인이 필요합니다.

### 현재 기준

OntoFlow는 `Gate`를 코어가 아니라 확장 컴포넌트로 봅니다. 코어는 일괄 등록과 직접 편집만으로도 동작해야 하며, Gate는 워크플로우가 만든 변경 후보를 승인 절차에 올리는 역할을 합니다.

```text
Workflow Manager -> 변경 후보 -> Gate 승인 -> Apply Boundary -> 실제 데이터 반영
```

### 의견을 받고 싶은 지점

- 어떤 변경은 즉시 반영하고 어떤 변경은 승인을 거쳐야 하는가
- 승인 화면에서 이전값, 후보값, 근거, 영향 범위를 어떻게 보여줄지
- Gate가 없어도 안전하게 운영 가능한 최소 통제선은 무엇인지

### 예시 질문

승인 절차는 코어 기능이어야 할까요, 확장 컴포넌트여야 할까요?

## 5. 공개 용어

### 배경

OntoFlow는 온톨로지, 워크플로우, 상태 이력, 검증, 승인 경계가 함께 등장합니다. 용어가 어렵거나 특정 제품의 용어처럼 보이면 신규 참여자가 맥락을 잡기 어렵습니다.

### 현재 기준

공개 문서에서는 쉬운 표현을 먼저 두고, 필요한 경우 기술 용어를 함께 둡니다.

```text
TBox = 클래스 타입 영역
ABox = 인스턴스 영역
ObjectType = 업무 객체의 클래스 타입
ObjectInstance = 실제 업무 객체 인스턴스
ActionType = 실행 가능한 업무 작업 정의
```

### 의견을 받고 싶은 지점

- 일반 사용자에게 가장 자연스러운 한국어 표현
- 개발자가 구현 문서에서 혼동하지 않는 영문 식별자
- 한국어 기준 문서와 영어 요약 문서의 용어 대응

### 예시 질문

외부 문서에서는 어떤 용어가 가장 명확할까요?

## 의견 남기는 방식

의견은 GitHub Discussions에 질문 단위로 남기는 것을 권장합니다.

좋은 의견 형식:

```text
주제: 워크플로우 상태 전달
상황: 병원 예약처럼 여러 단계에서 같은 환자와 예약 후보를 참조합니다.
의견: 상태 슬롯은 추적에는 좋지만, 화면에서는 노드 간 데이터 흐름도 같이 보여주면 이해가 쉬울 것 같습니다.
이유: 운영자는 값의 저장 위치보다 "어느 단계에서 생겨 어디로 갔는지"를 먼저 봅니다.
```
